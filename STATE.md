- **Outils de diagnostic (session 8)** : `experiments/spike_surface_min.cpp` (+ `.manifest`/`.rc`) — reproducer Win32 pur, aucune Qt, qui rejoue la séquence, imprime chaque retour/relecture et **compte lui-même** les pixels à l'écran ; `experiments/spike_exstyle_battery.py` — la même batterie en ctypes (A/B Python vs C++).

## Décisions actées (détail dans `docs/technique.md`)

1. Cible **Windows 10/11 x64** uniquement en v1 (Fences est Windows-only).
2. Stack : **C++17 + Qt 6.8 (Widgets)**.
3. Masquage des icônes natives et rendu maison (ADR-3) ; sur Win11, masquage réversible via `ShowWindow(SW_HIDE)` sur `SHELLDLL_DefView`.
4. **ADR-4** : fenêtres enfants de `Progman`, insérées sous `SHELLDLL_DefView`, **obligatoirement `WS_EX_LAYERED`** (`SetLayeredWindowAttributes` alpha=255) — sinon non composées par DWM (échec silencieux). Pas de WorkerW, pas de Tk pour le produit.
5. Persistance JSON versionnée atomique ; les fichiers ne sont jamais déplacés sans opt-in.
6. Local-first : zéro télémétrie.
7. **Portage Qt (T-016)** : garde `WM_WINDOWPOSCHANGING` (aucun restack au-dessus des icônes) + watchdog 2 s au lieu des broadcasts `WM_SETTINGCHANGE`/`WM_DISPLAYCHANGE` (non reçus par une fenêtre enfant).
8. **Session 7** : le flag layered doit être voulu par Qt (`setWindowOpacity(0.99)`), jamais ajouté après le reparentage (refus silencieux de Windows) ; `attach()` **vérifie** au lieu de poser.
9. **T-004** : le Shell est l'autorité pour les chemins (`SHGetKnownFolderPath`) et les noms affichés (`SHGFI_DISPLAYNAME`) ; les icônes passent par la liste d'images système, pas `SHGFI_ICON` (32 px trop petit).
10. **Session 8 — chemin de rendu (§7 piste (a))** : une **surface Win32 brute** (`DesktopSurface`) possède le HWND et blitte sur `WM_PAINT` une image produite par Qt hors écran. Qt ne peint jamais dans une fenêtre hébergée. Conséquence : ADR-2 (Qt Widgets) est intact, mais Qt n'est plus responsable du blit.
11. **Session 8 — manifeste applicatif obligatoire** : `starfish.exe` doit embarquer `src/starfish.manifest` (via `src/starfish.rc`). Sans lui, `WS_EX_LAYERED` est refusé sur les fenêtres enfants et **rien ne s'affiche**, sans le moindre message. Corollaire : le flag est **aussi** posé dès `CreateWindowExW`, pour survivre à un binaire sans manifeste.
12. **Session 9 — T-017, les deux modes layered sont mutuellement exclusifs** : `SetLayeredWindowAttributes(LWA_ALPHA)` est une porte à sens unique — après cet appel, tout `UpdateLayeredWindow` échoue (err 87), même sur notre propre fenêtre. ULW fonctionne sinon **même sur un enfant cross-process de Progman** (spikes `experiments/spike_ulw*.py`). Mode per-pixel de `DesktopSurface` : `attach()` saute l'appel d'attributs, frames poussées via ULW, repli opaque automatique. Détail : `docs/technique.md` §8.
13. **Session 10 — la validation T-021/T-017 à l'écran n'est pas faisable depuis l'agent** : le bureau de l'utilisateur est typiquement recouvert par d'autres fenêtres, et le `Win+D` envoyé par la sonde (`keybd_event`/`SendInput`) est sans effet depuis un processus non-foreground / sandboxé — Windows ne minimise pas les autres fenêtres. Les sondes s'auto-valident par diff de pixels (`PrintWindow` relecture + diff baseline/shown) ; quand le bureau n'est pas visible, le diff est dominé par les fenêtres autour (mesuré : bbox 2467×1271, pixel central = papier peint), pas par la zone. Le `offscreen`/`readback` confirment que la pipeline de rendu est saine (panneau `0x1f2937` peint dans le HWND) ; c'est la **combinaison bureau libre + yeux de l'utilisateur** qui manque. Conclusion : T-021/T-018/T-019 sont par nature des validations humaines.
14. **Session 10 — toolchain agent** : `export PATH` dans le bash agent ne suffit pas à résoudre `libstdc++-6.dll` pour l'exe MinGW (sandbox MSYS2). Symptômes : `error while loading shared libraries: libstdc++-6.dll` ou `rc=127`/`SIGTERM`. Contournements : `dangerouslyDisableSandbox: true` (le loader natif trouve alors les DLL) ou lancer via PowerShell avec `$env:PATH = "C:\Users\<user>\Qt\6.8.3\mingw_64\bin;C:\Users\<user>\Qt\Tools\mingw1310_64\bin;" + $env:PATH`. Le tool PowerShell **n'affiche pas le stdout** d'un exe GUI, mais ses *fichiers* (QFile, QImage::save) arrivent → faire écrire les diagnostics dans un fichier. `ctest` via bash hangue, via PowerShell passe en 0,6 s.
15. **Session 13 — T-007 : la géométrie des zones est pure, le propriétaire est le conteneur.** `FenceGeometry` (`src/ui/fence_geometry.hpp`) ne connaît ni widget ni Win32 (14 cas testés) ; `FenceContainer` est le seul objet qui sait combien de zones existent et où elles sont. Conséquence : une `FenceView` **ne se déplace jamais elle-même** — elle signale un geste, le conteneur décide. C'est aussi ce qui débloquera le drag-drop **inter-zones** (T-006-2 reste intra-zone).
    - Règles retenues : **les coins gagnent sur les bords** dans `hitTest` (sinon le redimensionnement diagonal est inatteignable sur une petite zone) ; un redimensionnement ouest/nord **épingle le bord opposé** (la zone rétrécit, elle ne se retourne jamais) ; l'aimantation cible les bords **et le centre** de l'écran **et** de chaque autre zone à 8 px ; après aimantation `clampToBounds` garantit que la zone reste **entièrement à l'écran** (une zone traînée hors écran serait irrécupérable à la souris).
    - `FenceContainer` a un **mode headless** (aucun bureau requis) : c'est ce qui rend la sonde `--fence-demo` et d'éventuels tests possibles sans écran.
    - **Piège d'exécution confirmé** : le sandbox bloque le lancement de `starfish.exe` même avec le bon `PATH` en PowerShell (`$LASTEXITCODE` vide, aucun fichier écrit, aucune erreur visible). Il faut `Start-Process -Wait` **avec `dangerouslyDisableSandbox: true`** pour qu'un exe GUI s'exécute et écrive ses fichiers. Le binaire est en `build/starfish.exe`, pas `build/src/starfish.exe` (`qt_add_executable` le place à la racine de `build/`).
16. **Session 14 — T-008 : le layout est la seule autorité sur le contenu d'une zone, et l'écriture est différée** (détail : ADR-7 et §10 de `docs/technique.md`).
    - **Deux pièces, comme pour la géométrie** : `core::JsonStore` ne connaît que le **format** (schéma 1, écriture atomique, sérialisation déterministe), `core::LayoutStore` possède le **document** (chemin, chargement, moment de l'écriture). Aucun des deux ne connaît les widgets ou Win32 → testables sans écran.
    - **Aucune écriture sans changement** : `setLayout()` sérialise le candidat et le compare au document courant ; identique → `false`, pas de timer, pas d'I/O. **Aucune écriture en rafale** : un drag émet ~60 `fenceRectChanged`/s, le timer (500 ms) est réarmé à chaque changement → un geste = **une** écriture (mesuré : rafale de 6 signaux → 1 écriture ; sélection qui change → 0 écriture).
    - **Le document, pas le disque, décide de ce qu'une zone affiche** : une entrée restaurée dont le fichier a disparu est **conservée** (nom déduit du chemin). Le scan du bureau ne sert qu'à *résoudre* les métadonnées d'affichage, jamais à composer les zones. Le resolver d'items est **injectable** (`setItemResolver`) : défaut sans Shell (testable, headless), `DesktopScanner::itemForPath` en production — le même resolver sert aux drops de l'Explorer, donc un seul chemin de résolution.
    - **Un fichier illisible/tronqué/de schéma inconnu est refusé et le layout courant est conservé** (jamais remplacé par du vide) ; l'erreur est remontée (`load` / `saveFailed`), pas avalée.
    - `applyLayout()` **remplace** les zones (détruites, jamais les fichiers) en conservant leurs **ids d'origine**, et avance le compteur d'ids au-delà du plus grand numéro restauré : une nouvelle zone ne peut pas usurper l'id d'une zone restaurée.
    - **Persisté mais pas encore agi** (le schéma ne bougera donc pas quand ces tâches arriveront) : `monitor` (T-014), `rolledUp` (F-020 / T-009), l'alpha de `style.background` (T-017). Le rayon et le RGB du fond sont, eux, appliqués.
17. **Session 15 — T-009 : la navigation change ce qui est *visible*, jamais ce qui est *stocké*** (détail : ADR-8 et §11 de `docs/technique.md`).
    - **Le rect stocké reste le corps déplié.** `FenceGeometry::visibleRect(stored, rolledUp)` dérive le rect affiché, `applyRequest()` fait tout le calcul : aimantation et clamp sur le rect **visible**, hauteur dépliée préservée. Enrouler/dérouler est donc **sans perte** et le schéma JSON n'a pas bougé (`rolledUp` y était depuis T-008).
    - **Le widget ne s'enroule pas lui-même**, pas plus qu'il ne se déplace : double-clic ou molette sur la barre de titre → `rollUpRequested(bool)` → le conteneur applique. Même règle qu'en T-007.
    - **L'état de navigation doit survivre au watchdog 2 s.** `place()` de `DesktopSurface` tient compte de `m_visible` (quick hide) et de `m_raisedAboveIcons` (Peek), et la garde `WM_WINDOWPOSCHANGING` n'autorise `HWND_TOP` qu'en Peek. Sans ça, une zone masquée réapparaîtrait toutes les 2 s.
    - **Peek = au-dessus de la couche d'icônes, pas au-dessus des fenêtres.** `HWND_TOP` est le point le plus haut atteignable pour un enfant de `Progman` (ADR-4). Flotter au-dessus des fenêtres d'application exigerait un modèle top-level → **T-029**, assumé et documenté.
    - **Quick hide n'a pas encore son geste d'origine** (double-clic sur le bureau **vide**) : la zone vide appartient à `SysListView32`, il faut un hook souris global → **T-028**. L'état et le câblage sont faits et testés ; le déclencheur est un hotkey.
    - **Les hotkeys se heurtent au système** : `Win+Space` (F-021) est refusé par Windows, qui le réserve au sélecteur de langue — mesuré, pas supposé. Quick hide s'enregistre sur `Win+Shift+H`. Raccourcis configurables → **T-030** (F-033).
    - **Piège de sonde** : `check(étape, mutation() && lecture(), détail(lecture()))` a un **ordre d'évaluation d'arguments non spécifié** → le détail peut être construit avant la mutation et afficher une valeur périmée alors que le test passe. Toute mutation doit être une instruction à part. Et `QRect::bottom()` est **inclusif** (`y + h - 1`) alors que `snap()` aligne sur `y + h` : ne pas mélanger les deux dans une assertion.
18. **Session 16 — le binaire est autonome (déploiement du runtime Qt)** : `build/starfish.exe` refusait de démarrer hors de l'environnement Qt (« Qt6Widgets.dll introuvable »), parce qu'un build MinGW **lie Qt dynamiquement**. Une étape `POST_BUILD` (`windeployqt`, localisé via le dossier de `Qt6::qmake`) copie désormais les DLLs Qt, le plugin `platforms/qwindows.dll` et le runtime MinGW (`libstdc++`, `libgcc_s`, `libwinpthread`) à côté de l'exe. `POST_BUILD` ne tire qu'au relink → gratuit en incrémental. Vérifié avec un `PATH` réduit à `C:\Windows\System32` : `--nav-demo` et `--nav-demo --host` (29/29) passent. Même famille de problème que le manifeste : une dépendance **porteuse**, invisible en développement, qui casse tout pour qui essaie le binaire.
    - **Piège de sonde** : les rapports s'écrivent en **chemin relatif** (`build/xxx_demo.txt`) → lancer les sondes **depuis la racine du dépôt**, sinon le rapport part dans `build/build/` et l'ancien reste périmé, avec un `exit 0` trompeur. Si `build/` n'existe pas sous le CWD, `QFile` échoue **en silence**.
19. **Session 17 — T-010 : les règles décident quelle zone *montre* un item, et ne touchent jamais au disque** (détail : §12 de `docs/technique.md`). Trois pièces, découpées comme les précédentes :
    - `core::RuleEngine` = **décider** (pur, `now` injectable) ; `core::DesktopWatcher` = **déclencher** (Qt Core seul, diff pur + debounce) ; `FenceContainer::applyRulesTo()` = **appliquer** (le conteneur est déjà propriétaire des zones). Aucune des trois ne connaît les widgets, et les deux premières se testent sans écran.
    - **Critères ET-és, première règle gagnante.** Les dates sont **relatives à maintenant** (`newerThanDays` / `olderThanDays`, bornes exactes) et non des horodatages absolus : une règle garde son sens dans le temps et après un export/import. Un `modified` **invalide ne satisfait pas** un critère de date (il ne doit pas tomber dans « plus vieux que 30 jours » par accident).
    - **Le nom comparé est celui du disque, extension comprise** — jamais le nom d'affichage du Shell, qui masque l'extension des types connus (« photo.png » s'affiche « photo »). Un critère de type qui ne verrait pas l'extension ne correspondrait **jamais**. C'est le rôle de `core::fileMetaFromItem()`.
    - **La règle d'or tient par construction** : `applyRulesTo()` range l'item dans une zone et **ne déplace aucun fichier**. `moveFiles` est persisté et relu mais **sans effet** — le déplacement réel sur disque est **T-031**, volontairement non implémenté (une règle mal écrite qui relocalise des fichiers est irréversible). La sonde le **prouve** : après application, le fichier est toujours à son chemin d'origine.
    - **Idempotence** : un item déjà dans la zone visée (chemins comparés sans tenir compte de la casse) n'est pas ajouté deux fois — sinon une notification répétée re-rendrait la zone et réécrirait le document pour rien. Une règle visant une zone supprimée est **signalée et ignorée**, l'item reste où il est.
    - **Les règles appartiennent au document** (`Layout::rules`, tableau `rules` du §5) : sauvegardées, restaurées et exportables avec les zones. Le schéma reste **1** (`rules` était réservé depuis l'origine) et un document **sans** `rules` — ce que T-008 écrivait — continue de se charger.
    - **Le watcher prend sa ligne de base au démarrage** : les entrées déjà présentes ne sont **pas** signalées, sinon une règle re-rangerait tout le bureau à chaque lancement. Le diff est calculé **au moment du debounce**, pas à la réception de l'événement : un fichier créé puis supprimé dans la fenêtre n'est jamais signalé.
    - **Sonde sûre par conception** : `--rules-demo` nomme les fichiers qu'il crée d'après son PID (il ne peut donc pas écraser un fichier existant), ne supprime **que** ce qu'il a créé, et n'efface jamais un dossier qu'on lui pointe via `--watch`.

20. **Session 18 — T-011 : un portail reflète un dossier, le document n'en stocke que le chemin** (détail : §13 de `docs/technique.md`).
    - **Trois pièces, comme les fois précédentes** : `core::Portal` / `listPortal()` = **lister** (Qt Core + FS local, aucun appel Shell, donc testable sans bureau) ; `FenceContainer::addPortal` / `refreshPortalsFor` = **appliquer** ; `DesktopWatcher::folderChanged()` = **déclencher**.
    - **Le listing n'est jamais persisté.** `toLayout()` retire de la liste des items tout chemin qu'un portail fournit et écrit à la place `{"kind":"portal","path":…}`. Persister les tuiles ferait deux dégâts : des doublons au rechargement (la zone recevrait la liste persistée **et** le listage frais), et surtout un miroir **gelé** — un fichier ajouté au dossier n'apparaîtrait plus.
    - **Le chemin du dossier est conservé verbatim.** `QDir::cleanPath()` convertit `C:\x` en `C:/x` : nettoyer le chemin ferait diverger le document de lui-même et casserait l'aller-retour octet pour octet (§10). La comparaison de deux dossiers passe par `core::sameFolder()`.
    - **Un dossier injoignable n'est pas fatal** : `Portal::error` est renseigné, la liste est vide, l'entrée **reste dans le document**. Un disque débranché ne doit pas effacer le portail de l'utilisateur.
    - **Le miroir a besoin de savoir qu'un fichier est parti.** `itemsAdded()` ne signale que les ajouts ; un portail **re-liste**, donc il lui faut un signal indifférent au type de changement : `folderChanged(folder)`, après le même debounce. Corollaire : la ligne de base est **élaguée** des entrées disparues, sinon un fichier supprimé puis recréé ne serait plus jamais « nouveau ».
    - **La règle d'or tient, et la moitié « écriture » de F-024 est assumée comme non faite** : déposer un fichier sur une zone-portail l'ajoute comme tuile à la zone, il ne le range **pas** dans le dossier. Écrire = `QFile::rename` = mutation irréversible du disque → **T-036**, même raisonnement que T-031.
    - **Piège de ré-entrance, trouvé par la sonde** : `appendItems()` émet `contentChanged()`, que le produit écoute pour **lire `toLayout()` et sauvegarder**. Le portail était enregistré **après** l'ajout de ses tuiles → le document lu au moment du signal portait les 4 fichiers comme items `"file"` et **aucune entrée `"portal"`** : le portail disparaissait au redémarrage et le premier rafraîchissement du dossier réécrivait le document. **L'état doit être cohérent *avant* le signal, jamais après** — le portail est donc enregistré avant ses tuiles, et la sonde garde une vérification qui rejoue la lecture **pendant** l'émission.
    - **Piège de sonde (suite de la décision 17)** : `QFileInfo("…/build/dossier").absolutePath()` renvoie le **parent** (`…/build`), pas le dossier. Pour vérifier qu'une tuile est bien *dans* le dossier, comparer `QFileInfo(item.path).absolutePath()` (le parent de la tuile) avec `QDir(folder).absolutePath()` (le dossier).

21. **Session 20 — T-012 : une snapshot est une disposition *plus une enveloppe*, et l'enveloppe se détecte en la parsant** (détail : §14 de `docs/technique.md`).
    - **Un seul format, pas deux.** Un fichier de snapshot est le document schéma 1 **plus** `snapshot: {createdAt, note}`. Restaurer = `applyLayout(snapshot.layout)` ; exporter = écrire le document tel quel ; importer = `JsonStore::load`. Aucun second format à tenir synchronisé, et `JsonStore` n'a pas eu à apprendre les snapshots.
    - **L'id est un nom de fichier, pas un champ du document.** `isValidSnapshotId` refuse séparateurs, `:`, jokers, `.`/`..`, espace initial et point final — Windows rogne ces derniers, donc deux ids entreraient en collision sur disque ; un id hostile ne doit pas pouvoir écrire hors du dossier `snapshots/`.
    - **Le dossier `snapshots/` est à côté du document** (`SnapshotManager::snapshotsDirFor`) : `--layout FILE` déplace donc zones **et** snapshots ensemble, et rien ne s'égare d'un profil à l'autre.
    - **⚠️ Piège corrigé (le plus important de la session)** : le garde-fou « ce fichier est-il une snapshot ? » lisait les **4096 premiers octets**. Or `QJsonObject` **trie ses clés**, donc `snapshot` est écrit **en dernier** : au-delà de ~4 Ko il ne trouvait rien, `exportLayout` **écrasait** une snapshot et `importLayout` l'**avalait** — en silence. Le test passait, parce que sa disposition témoin faisait moins de 4 Ko. Corrigé par un **parsing JSON** (`hasSnapshotEnvelope`), insensible à la taille. Le test `largeSnapshotIsNotALayoutFile` **prouve la prémisse** (le marqueur est bien au-delà des 4096 premiers octets) : il resterait rouge avec l'ancien code. Leçon : **ne jamais décider du contenu d'un JSON en lisant un préfixe d'octets**.
    - **Une sonde ne laisse rien derrière elle** : `--snapshot-demo` supprime la snapshot **et** le fichier exporté qu'il a écrits, y compris dans le vrai `%APPDATA%` quand `--layout` est absent (2 vérifications dédiées dans le rapport). Même discipline que `--rules-demo` / `--portal-demo`.
    - **`QLatin1String(...).arg(<entier>)` ne compile pas** : `QLatin1String` n'a pas de surcharge entière et la conversion vers `QChar` est ambiguë (échec sur `src/main.cpp`). Passer `QString::number(...)` — c'est déjà le style du fichier.

22. **Session 21 — T-038 : le produit, c'est une séquence, et la capture souris était le vrai blocage** (détail : §15 de `docs/technique.md`).
    - **`ProductApp` n'ajoute pas de moteur, il câble ceux qui existaient.** Sa responsabilité propre est l'**ordre** : lire le document *avant* la première frame, appliquer, héberger, surveiller, et tout réécrire en sortant. Les pièces gardent leur comportement ; le produit ne fait que les enchaîner.
    - **Le tray et les réglages ne décident de rien**, comme tous les autres widgets du projet : `TrayIcon` et `SettingsDialog` émettent, `ProductApp` applique. Même règle que « le widget signale, le conteneur décide » (décision 15).
    - **⚠️ Le déplacement des zones était cassé, et personne ne le savait** : `DesktopSurface::forwardMouse` routait bien la souris, mais **rien ne prenait la capture**. Windows cesse d'envoyer `WM_MOUSEMOVE` dès que le curseur sort du rectangle visé — un déplacement de barre de titre mourait donc au premier pixel franchi, et une zone hébergée était **impossible à bouger**. C'était l'écart n°6 de l'audit, invisible en headless parce que la sonde envoyait ses `QMouseEvent` directement au widget. Ajouté : capture au press, relâchement au button-up, et `WM_CAPTURECHANGED` → `releaseStuckGesture()` qui poste les relâchements manquants. Leçon : **un test qui poste ses propres événements ne peut pas valider le routage de la souris** ; seule une capture ou un geste humain le peut.
    - **On ne restaure que ce qu'on a masqué.** La première version appelait `ShowWindow(SW_SHOW)` sur `DefView` au shutdown sans condition : un utilisateur qui avait caché ses icônes lui-même les aurait vues réapparaître. `ProductApp` tient `m_iconsHidden` et ne restaure que dans ce cas — et le dit : si l'appel échoue, la case reste décochée plutôt que de mentir.
    - **Le masquage des icônes natives est recâblé au bon endroit** (écart n°5) : statique sur `DesktopSurface` plutôt que sur `DesktopHost`, qui n'est plus le chemin de rendu.
    - **`tr()` avec des chaînes sources en anglais** : F-036 / T-014 (i18n en/fr) devient un fichier de traduction au lieu d'une chasse. L'interface est donc **en anglais** pour l'instant, et c'est assumé.
    - **L'interface est un ajout au plan** : T-038 occupe la Phase 5, à côté de T-013/T-014. Elle avait été identifiée par l'audit (écart n°1 : « le projet livre un moteur, pas un produit »).
    - Limites assumées : créer une zone par un **geste sur le bureau vide** (F-001) demande un hook souris global, donc la création passe par le tray et les réglages (**T-028**) ; quick hide n'a toujours pas son geste d'origine (T-028) ; hotkeys en dur (T-030) ; pas de lancement au démarrage (F-035).

23. **Session 22 — T-014a : le multi-écran est un modèle pur, et le DPI tient en deux frontières** (détail : §16 de `docs/technique.md`).
    - **Arbitrage P0/P1 (2026-10-15)** : `docs/produit.md` §6 classe **F-032 en P0** et §7 la met dans **v0.1 (MVP)**, alors que `TODO.md` portait une ligne unique T-014 en Phase 5 / **P1** empilant en plus l'i18n (**F-036**, P1/v0.2) et les thèmes (**F-004**, P0 — mais `iconSize`/`padding`/`gap`/`titleBar` sont persistés **et inertes**). **Décision : scinder** — T-014a (multi-écran + DPI) garde le **P0** et se fait maintenant ; T-014b (i18n FR + thèmes) passe en **P1 / v0.2**. `produit.md` n'est **pas** réécrit. *(Appliqué sans réponse de l'utilisateur : question posée, délai expiré — **à confirmer** ; inverser ne coûte qu'une ligne de `TODO.md` et deux de `plan.md`.)*
    - **Tout StarFish est en pixels PHYSIQUES** — rects, document, `SetWindowPos`, `UpdateLayeredWindow`, messages souris : c'est l'espace client de `Progman`, donc celui de Win32, le primaire à (0,0) et des coordonnées **négatives** possibles pour un écran placé à gauche ou au-dessus. Qt reste en **logique** ; `devicePixelRatio` est franchi à **deux** endroits seulement (frame rendu, souris reçue). À 100 % les deux espaces coïncident — c'est pourquoi la v1 n'a jamais vu le problème.
    - **Une zone appartient à l'écran de son centre, et y est entièrement clampée** — jamais dans la **zone morte** du rectangle englobant quand deux écrans ont des tailles différentes (invisible, donc irrattrapable à la souris : le raisonnement de T-007 appliqué au multi-écran). L'aimantation cible **chaque** écran, donc le bord **interne** du moniteur voisin.
    - **Un écran qui disparaît ne perd pas ses zones** : `restoreRect` (rect encore valide → inchangé ; sinon l'écran **enregistré** ; sinon le plus proche ; sinon le primaire), déclenché par `screenAdded`/`screenRemoved`/`primaryScreenChanged` → `revalidateScreens()`, qui n'émet `fenceRectChanged()` **que** pour les zones réellement déplacées (sinon le document se réécrirait pour rien). `monitor` est **dérivé du rect**, jamais l'inverse.
    - **La séparation est conservée** : `screen_layout.hpp` est **pur** (aucun `QScreen`, aucun Win32) → un arrangement DPI mixte à deux écrans se teste **sans deux écrans** ; les surcharges `QSize` de `FenceGeometry` survivent en **délégateurs**, donc une seule implémentation et zéro changement d'appelant.
    - **Ce qui n'est PAS établi** (ne pas le présenter comme acquis) : aucune sonde `--screen-demo` ; la mise à l'échelle de la peinture par Qt n'est prouvée par **aucune mesure** ; le multi-écran réel et le menu contextuel sur écran à 150 % sont des validations **humaines**.

25. **Session 24 — T-014a : la sonde lit l'environnement, et la mise à l'échelle de la peinture se mesure** (détail : §16 de `docs/technique.md`).
    - **Une sonde rapporte ce qu'elle *lit*, pas ce qu'on croit.** `--screen-demo` imprime l'arrangement réel **lu** chez Qt (1 écran, `dpr 1`, DPI système 96) et le **contexte d'awareness DPI réellement obtenu** — `DPI_AWARENESS_PER_MONITOR_AWARE (2)`. Ce n'est **pas** `PER_MONITOR_AWARE_V2`, que l'on prêterait volontiers à Qt 6 : c'est ce que Windows a accordé après la demande de Qt, et le manifeste ne déclare rien (ADR-4). Le contexte est résolu par `GetProcAddress` (`GetThreadDpiAwarenessContext` / `GetAwarenessFromDpiAwarenessContext`) : la déclaration est gardée par `WINVER` dans le SDK, et la sonde doit se compiler sur n'importe quelle toolchain.
    - **⚠️ La mise à l'échelle de la peinture n'était établie par aucune mesure** — toute la logique DPI repose sur elle. Mesure falsifiable ajoutée : une bordure de **1,0 pixel logique** (pen largeur 1,0) doit couvrir **`dpr`** pixels physiques une fois peinte. La couverture est comptée sur le **canal bleu** (remplissage `#1F2937` → 55, bordure `#3B82F6` → 246), en **fraction**, pour que le pixel à demi couvert d'un ratio 1,5 soit compté au lieu d'être arrondi. Trouvé : **1,00 / 1,50 / 2,00** px à `dpr` 1 / 1,5 / 2.
    - **La prémisse est prouvée, et pas seulement affirmée** : en neutralisant la conversion dans `renderFence` (test temporaire, revert), la mesure tombe à **1,00** (dpr 1,5) et **0,00** (dpr 2 — la colonne échantillonnée tombe alors **hors** du widget non mis à l'échelle) : **deux `FAIL`**. Sans cette preuve, la mesure aurait pu être verte pour la mauvaise raison (même leçon que la régression des 4 Ko, décision 21). Leçon : **une mesure qui ne peut pas échouer ne mesure rien.**
    - **Les arrangements qui cassent sont construits, pas attendus** : la machine de dev n'a qu'un écran, donc la sonde assemble les configurations (moniteur à gauche → **coordonnées négatives**, moniteurs de tailles différentes → **trou** que le *bounding box* contient mais qu'aucun moniteur ne dessine, DPI mixte) et les fait passer par un **vrai** `FenceContainer`. L'existence du trou est **vérifiée** (un point qui n'appartient à aucun écran), sinon le test de clamp serait vacun — un test doit prouver sa prémisse.
    - **Ce qui reste est matériel, pas logiciel** : le multi-écran réel, le DPI mixte et le placement du menu contextuel Shell à 150 % exigent deux écrans et des yeux. Même famille que T-021 / T-017 visuel.

26. **Session 25 — ADR-9 : l'édition manuelle est une demande produit, et le z-order est le mur** (détail : ADR-9 et §17 de `docs/technique.md`).
    - **Ce que l'utilisateur veut (dit en session 25)** : créer des zones quand il veut, y déposer les icônes qu'il veut, **organiser à la main**, et qu'une zone déplacée **emporte ses icônes**. L'**auto-organisation n'est pas demandée** → T-031/T-032 ne sont pas à reprendre ; le produit ne se juge pas sur les règles.
    - **« Les icônes suivent la zone » était déjà vrai, et c'est maintenant prouvé** : `renderFence` produit une image **du rectangle de la zone** (aucune coordonnée écran), donc rendre la même zone avant et après déplacement donne des images **identiques octet pour octet**. Vérification `moving a fence carries its tiles`, avec sa **prémisse** (le rect a changé) pour ne pas passer sur une zone immobile.
    - **⚠️ Le mur, mesuré : sous la couche d'icônes, une zone ne reçoit pas la souris.** Au centre d'une zone hébergée, la fenêtre **visible** la plus haute est `SHELLDLL_DefView` (layered), puis `SysListView32` (plein écran, **plain**), puis nous — **icônes natives masquées**, c'est nous. Donc **masquer les icônes natives (ADR-3) n'est pas cosmétique : c'est la condition pour qu'une zone serve à quelque chose.** Vérification **falsifiable** (elle exige les deux moitiés), et la sonde **restaure les icônes aussitôt**. Piège de sonde rencontré : sans filtrer `IsWindowVisible`, une fenêtre **masquée** reste dans l'énumération et la mesure ne distingue plus « masquée » de « rien n'a changé ».
    - **La décision (ADR-9, option A)** : StarFish **possède la couche d'icônes** pendant qu'il tourne — couche native masquée au démarrage, et **il dessine toutes les icônes** : celles des zones (fait) **et celles qui n'y sont pas** (surface de fond plein écran, **T-039**). Les icônes hors zone sont **calculées** (*toutes les entrées − celles qu'une zone détient*), **jamais stockées** : ADR-7 reste intact, **le schéma du document ne bouge pas**, et F-007 (supprimer une zone **rend** ses icônes) comme F-011 (sortir une icône) en **découlent** au lieu d'être des fonctions à écrire (**T-040**).
    - **Corollaire qui économise une tâche** : les gestes « sur le bureau vide » (F-001 créer, F-022 quick hide) arrivent alors **directement à notre surface de fond** → **le hook souris global de T-028 n'est plus nécessaire** pour eux (**T-041**).
    - **Alternative écartée (option B)** : garder la couche native visible et poser les zones **au-dessus**. Moins de travail, mais un fichier rangé dans une zone apparaîtrait **deux fois** (icône native + tuile) — c'est exactement ce que l'utilisateur veut éviter. Écartée **par la duplication**, pas par le goût. Prix de l'option A, assumé : réimplémenter renommage/couper-coller des icônes hors zone (menu contextuel déjà là) et rendre `DefView` même en cas de plantage (**T-042**).
    - **À confirmer** : l'option A engage le produit (le bureau passe sous notre rendu). Elle suit la demande, mais **l'accord de l'utilisateur est requis avant d'écrire T-039**.

27. **Session 26 — T-043/T-044 : le geste se mesure à l'écran, et une seule instance** (détail : §9 et §15 de `docs/technique.md`). Le bug a été **trouvé par l'utilisateur au vrai curseur**, pas par une sonde — c'est la leçon de la session.
    - **Symptôme rapporté** : « je suis obligé de cliquer sur *Hide Desktop Icons* pour pouvoir la déplacer ; et quand je le fais, ça le fait mais pas très très bien, c'est un peu bizarre. » La première moitié **confirme la mesure** d'ADR-9 (sous la couche d'icônes visible, une zone ne reçoit pas le clic) ; la seconde était un **bug**.
    - **⚠️ Cause : le delta du geste était mesuré dans un repère qui se déplace.** `FenceView::mouseMoveEvent` utilisait `event->pos()`, une position **relative au widget** — or le widget (et la surface hébergée qui le porte) **se déplace sous le curseur** pendant le geste. Chaque événement décrit donc le curseur par rapport à une fenêtre qui l'a déjà suivi : le déplacement appliqué vaut `réel − appliqué` et **converge vers la moitié** de la distance, en saccades. **La zone se déplaçait de la moitié** de ce que la souris parcourait.
    - **Correctif** : la référence du geste est prise **à l'écran** (`event->globalPosition()`), le seul repère qui ne bouge pas avec la fenêtre. La surface poste déjà des positions écran **physiques** et le conteneur raisonne en physique → les deux espaces coïncident, et à 100 % rien d'autre ne change.
    - **Pourquoi aucune sonde ne l'avait vu** : elles envoient **un seul** `QMouseEvent` de déplacement — pas de boucle de rétroaction, donc rien à voir. La vérification ajoutée (`a multi-step drag lands where the cursor went`) livre un geste **réaliste** : 12 mouvements de (5,4), chaque événement rapportant le curseur **relatif au rect courant de la zone**, exactement comme Windows le fait sous capture. **Prémisse prouvée** : avec l'ancienne référence, la zone finit à **1230,924** au lieu de **1260,948** — la moitié, précisément.
    - **Règle générale** : un geste dont l'objet **se déplace** ne peut pas être mesuré dans le repère de cet objet, et une sonde qui n'envoie **qu'un** événement ne peut pas valider un geste. Le repère correct est l'**écran**.
    - **T-044 — deux instances trouvées vivantes** pendant le diagnostic (lancées sans argument à une minute d'intervalle). Elles se disputent le **document** (dernier écrivain gagne → des zones disparaissent) **et** l'**état des icônes natives** (chacune restaure ce que l'autre croyait masqué). `main()` prend un `CreateMutexW(L"Local\\StarFish.Desktop")` au démarrage du **mode produit** : la seconde copie journalise et sort `0`. Deux choix explicites : **mode produit seulement** (une application ouverte ne doit pas empêcher les **sondes** de tourner — c'est ce qui les rend utiles) et **sans boîte de dialogue** (un utilitaire de zone de notification qui ne fait rien au second lancement est le comportement attendu ; une boîte modale serait pire, et rendrait le garde non testable). Validé : première instance normale, seconde refusée.

28. **Session 27 — T-045 : les cellules de la grille sont locales au contenu, et une vérification bornée par un clip ne teste rien** (détail : §7 de `docs/technique.md`). Deuxième bug **trouvé par l'utilisateur** (capture à l'appui), et il valide au passage le correctif de T-043 (« le correctif vrai curseur fonctionne »).
    - **Symptôme** : « l'icône est à moitié cachée par la barre de titre ». Mesuré **dans l'image** : la coupure est exactement à `panelTop + 42`.
    - **⚠️ Cause** : `IconLayout::compute()` produit ses cellules dans l'espace **local au contenu** (`contentRect().top()` = `kTitleBarHeight + kPadding` = 42) — l'espace que `hitTest` consomme — mais `IconGrid::paint()` les dessinait **dans les coordonnées du widget**. La grille tombait 42 px trop haut et le `setClipRect(contentRect)` **tranchait la première rangée**. Correctif : `painter.translate(contentRect.topLeft())`, puis clip dans le repère local.
    - **Cause de fond, à retenir** : `paintDropIndicator` **translatait déjà** ses cellules. Deux consommateurs du même calcul, **un seul correct** : c'est l'incohérence interne qui a laissé passer le bug, et elle est invisible tant qu'aucune vérification ne compare le rendu à la géométrie.
    - **⚠️ Leçon de sonde, plus importante que le bug** : la **première** vérification écrite pour l'attraper **passait avec le bug en place** — elle comparait les pixels de la bande de la barre de titre (`y < kTitleBarHeight`), or cette bande est **au-dessus du clip** et reste vide quoi que fasse le painter. **Une vérification bornée par le clip ne teste rien** : l'instrumentation doit porter sur la plage où les pixels **faux** atterrissent. La version retenue exige que le premier pixel peint soit **strictement sous** le haut du contenu — avec le bug il vaut **exactement** ce haut (42), corrigé il vaut 54 — et elle est **agnostique des couleurs** (même zone rendue **avec** et **sans** ses tuiles, seule la différence est inspectée), donc aucune couleur d'icône n'est supposée.
    - **Corollaire** : le rendu d'une zone est désormais vérifié **par ses pixels** dans `--fence-demo`, pas seulement par sa géométrie. `--fence-demo` : **11/11** headless / **12/12** `--host`.

30. **Session 29 — T-046 : le filet est une note sur disque, et l'**ordre d'écriture** est la décision** (détail : §18 de `docs/technique.md`). Le filet se fait **avant** la surface de fond (session 28) ; il est posé.
    - **`core::IconHidingMarker`** (`src/core/icon_hiding_marker.{hpp,cpp}`, Qt Core seul, **8 cas**) : une note dans `%APPDATA%/StarFish/icons-hidden.marker` (le dossier du document — mais **pas** dans le dossier de `--layout` : la couche d'icônes appartient à la **session**, pas à un document). **La *présence* du fichier décide, jamais son contenu** : un marqueur illisible compte quand même.
    - **Deux ordres, choisis pour que le pire cas reste réparable** : marqueur **écrit avant** `SW_HIDE` (write-ahead), **retiré après** `SW_SHOW` (write-behind). Un plantage intermédiaire laisse toujours « marqueur sans masquage » — réparation sans effet — jamais « masquage sans marqueur », le seul état que rien ne répare. Et **un marqueur impossible à écrire refuse le masquage** (`setDesktopIconsHidden(true)` → `false`, `critical` ; la case du tray reste décochée). C'est ce refus qui rend la restauration inconditionnelle **sûre**.
    - **Le masquage et sa trace ne peuvent pas diverger** : `DesktopSurface::setDesktopIconsHidden` est le seul endroit qui masque/défait, et `DesktopHost::setIconsHidden()` / `iconsHidden()` **délèguent** désormais.
    - **Restauration inconditionnelle au démarrage** : `ProductApp::start()` appelle `repairIconHidingFromPreviousRun()` **avant tout le reste** et **quel que soit le mode** — elle ne dépend d'**aucun** état du processus mort, seulement du fichier ; si la restauration échoue, le marqueur est **conservé** (le prochain run, ou la sortie de secours, doit encore pouvoir réparer).
    - **Sortie de secours « Restore my icons »** (tray) : `TrayIcon::restoreIconsRequested` → `ProductApp::restoreDesktopIcons()` — une **commande, pas une bascule** (la bascule ordinaire n'agit que si l'état demandé diffère du **mémorisé**, donc elle est sans effet dans le cas précis où l'on a besoin d'elle ; la sonde le **prouve**). Seul endroit qui touche la couche réelle même en `--no-host` (déviation documentée).
    - **Sonde `--crash-demo` / `--crash-victim` : 20/20 PASS**, `rc=0`. Elle **masque les vraies icônes, tue le processus qui les a masquées**, lit les faits **de l'extérieur** (marqueur + `SHELLDLL_DefView`), **prouve que la fin était vraiment brutale**, vérifie qu'un `start()` neuf restaure **sans mémoire du crash**, puis mesure la sortie de secours. **Prémisse prouvée** : réparation neutralisée → `rc=1`, exactement 2 `FAIL`. Le rapport raté montre au passage la limite que la sortie de secours comble (`statusText` disait `desktop icons visible` alors que la couche était masquée).
    - **Imprécision assumée** : si l'utilisateur avait masqué ses icônes lui-même **avant** StarFish, la réparation les rendra visibles (une note sur disque ne peut pas mieux savoir ; rester sans icônes pour épargner une préférence serait pire). Risque résiduel : planter **et** ne plus jamais relancer → relancer Explorer.

32. **Session 30 — T-039 : les icônes hors zone sont *calculées*, et le fond est un *rôle* de surface, pas une seconde fenêtre** (détail : `devlog/2026-10-16.md`). C'est la tâche que l'ADR-9 option A rendait nécessaire — et elle ferme le mur du z-order.
    - **L'ensemble « ce qu'une zone ne détient pas » est recalculé à chaque changement et stocké nulle part.** Conséquences, et c'est tout l'intérêt : **ADR-7 reste intact** (le document ne décrit que des zones), **le schéma ne bouge pas**, et **F-007/F-011 en découlent sans code de restauration** — sortir une icône d'une zone, c'est *ne plus la détenir*, donc elle réapparaît sur le fond. La sonde le mesure (`deleting the fence puts the icons back` : 86 → 83 → 86).
    - **`DesktopSurface::Layer` remplace le booléen « au-dessus des icônes »** : `BelowIconLayer` (le placement des zones, ADR-4), `AboveIconLayer` (Peek, F-021) et **`Backdrop`** (le fond). `setRaisedAboveIcons()` **délègue** au rôle — donc **aucun appelant ne bouge** et le z-order mesuré par `--nav-demo` (`surface [1]` vs `DefView [0]`) est **inchangé**. Le rôle est honoré par `place()` **et** par la garde `WM_WINDOWPOSCHANGING` (invariant). Corollaire **mesuré** : il n'a **pas** fallu remonter les zones au-dessus de la couche d'icônes — la couche est **masquée**, et le fond se met **sous** les zones. « Les zones au-dessus des icônes » (session 28) est donc satisfait **sans toucher au placement des zones**, ce qui évite de casser les compteurs de trois sondes.
    - **Le fond est click-through et n'enregistre aucun `IDropTarget`.** `WM_NCHITTEST` → `HTTRANSPARENT`. Le fond peint des icônes mais n'en possède encore **aucun** comportement (T-042) : **avaler un clic ou un drop qu'on ne peut pas honorer serait une régression silencieuse.** Prix assumé et noté : **T-052** (déposer un fichier sur le bureau vide ne fait plus rien, puisque c'est `SHELLDLL_DefView` masquée qui le recevait) et **T-053** (le Peek n'a plus d'effet visible).
    - **On ne masque jamais la couche native sans un fond qui a prouvé son push per-pixel.** `attach()` rend d'abord, héberge, puis **relit `perPixelAlpha()`** : si `UpdateLayeredWindow` a échoué, `DesktopSurface` est déjà retombé sur le chemin opaque — et un fond plein écran **opaque** cacherait le papier peint. Le fond est alors refusé et `ProductApp` **laisse les icônes natives visibles**. C'est la même règle que le marqueur de T-046, appliquée à la deuxième chose dangereuse du projet : **si le geste sûr est impossible, on refuse le geste risqué.** Au retour, l'ordre inverse : **la couche native revient d'abord, le fond part ensuite** — jamais de bureau sans icônes, pas même une frame.
    - **T-017 est levé au passage.** Le chemin per-pixel était « codé, jamais validé visuellement » depuis la session 9. Le fond l'exerce sur une fenêtre **plein écran** enfant de `Progman`, et la sonde **mesure** que le push a réussi (aucun repli opaque) — première preuve à l'exécution de la conclusion de la session 9, et la validation à l'œil n'est plus qu'un confort.
    - **Le rendu est coalescé (120 ms).** Un drag de zone émet ~60 `fenceRectChanged`/s et chaque rendu téléverse l'écran virtuel entier (14 Mo) ; sans coalescence, déplacer une zone serait un test de bande passante.
    - **`ProductApp::screenLayout()` devient public** : c'est *la* définition des écrans pour ce processus ; une sonde qui s'en construirait une autre mesurerait un bureau différent de celui sur lequel le produit travaille.
    - **`--crash-demo` n'a pas pu être rejoué**, et ce n'est **pas** une régression : `QProcess` ne peut pas créer son tube stdio dans l'environnement de l'agent (`ERROR_PIPE_BUSY`), et l'échec est **identique sur la révision non modifiée** (`git stash -u` + rebuild). Le chemin a été exercé **à la main**, et plus probant que la sonde : `--crash-victim` seul → `backdrop hosted … 86 free icon(s)` → `marker written` → `native desktop icons hidden` ; `taskkill /F` → marqueur présent, icônes masquées ; `--product-probe` → **marqueur disparu, icônes rendues**, sans rien savoir du processus mort. Le filet de T-046 est donc exercé **pour de vrai**, sur un vrai `kill`.
    - **Vérification** : build MinGW **0 warning** ; `ctest` **12/12** ; `--backdrop-demo` **15/15** / **21/21** `--host` ; toutes les autres sondes **aux compteurs documentés** (`--fence-demo` 11/12, `--persist-demo` 26, `--nav-demo` 22/29, `--rules-demo` 28, `--portal-demo` 29/31, `--snapshot-demo` 11, `--screen-demo` 19, `--product-probe` 16) ; `%APPDATA%/StarFish/` **sans marqueur** et document utilisateur **non réécrit**. **Prémisse prouvée** : disposition forcée en lignes → `rc=2`, exactement deux `FAIL` (les deux cas de colonnes), les 12 autres verts.

33. **Session 31 — T-040 : sortir une icône est une *possession*, pas un état ; et le contenu doit être redessiné** (détail : `devlog/2026-10-16.md` et §20 de `docs/technique.md`). Le modèle de T-039 portait déjà la réponse ; ce qui manquait était le geste — et une chose que rien ne faisait.
    - **F-007 n'a demandé aucune ligne** : supprimer une zone, c'est ne plus détenir ses icônes, donc elles réapparaissent sur le fond. La sonde du fond le mesurait déjà depuis la session 30 (`deleting the fence puts the icons back`, 86 → 83 → 86). **F-011 est le même mouvement, une tuile à la fois** : on cesse de la détenir.
    - **Le geste est le drag sortant** (tirer une tuile **hors** de la zone, lâcher là) : c'est celui de Fences, il ne coûte **aucun hook global**, et il ne touche à rien — ni le fichier, ni le document au-delà d'une entrée en moins. La frontière entre les deux gestes est **une seule expression** (`rect().contains(release)`) et elle est vérifiée **des deux côtés** : lâcher dedans réordonne encore, lâcher dehors rend la tuile. Un indice visuel distinct (bordure pointillée + « release to put it back on the desktop ») dit lequel des deux est armé, et l'état est **recalculé à chaque mouvement** — revenir dans la zone redésarme le retour au bureau.
    - **Le widget signale, le conteneur décide** (règle de la session 13, tenue) : `FenceView::itemReleaseRequested(paths)` / `FenceContainer::releaseItems(id, paths)`. Une tuile qu'un **portail** fournit est **refusée** et journalisée : elle appartient au **dossier**, et le prochain rafraîchissement la remettrait aussitôt (T-011).
    - **⚠️ Correctif trouvé en chemin** : **une zone ne se redessinait jamais quand son contenu changeait**. `DesktopSurface` blitte une **image** rendue hors écran — le `paintEvent` du widget ne va jamais au bureau — et **rien** ne connectait `FenceView::contentChanged` à `renderFence`. Un fichier déposé, un rafraîchissement de portail ou une icône relâchée n'existaient donc que **dans le modèle**, jusqu'au prochain changement de géométrie (qui, lui, rendait). Corrigé par **une** connexion dans `addFence`, et les deux `renderFence()` explicites devenus redondants (`setFenceStyle`, `setFenceSort`) ont disparu : **un seul chemin mène le contenu à l'écran**.
    - **⚠️ Une vérification ne doit pas dépendre de la taille de l'écran du développeur.** Deux vérifications de la session 30 étaient rouges sur le bureau d'aujourd'hui — **1920×1080**, lu par Qt *et* par WinForms, donc pas un artefact de harnais : l'une écrivait un rect en dur dont le bas (1140) ne tient pas dans 1080, l'autre comparait la frame peinte à `< 10 %` de l'**écran** alors que **le dénominateur avait bougé, pas la frame** (231 738 px : 6 % à 2560×1440, 11 % à 1920×1080). **Vérifié sur la révision non modifiée** (`git stash` + rebuild) : **exactement les mêmes deux `FAIL`** → pas une régression. Corrigé par un rect **dérivé** de `desktopBounds()` et un seuil **dérivé** du **budget de pixels des cellules**.
    - **Vérification** : build MinGW **0 warning** ; `ctest` **12/12** (`ui_icon_grid` : **15 cas**) ; `--fence-demo` **17/17** headless / **18/18** `--host` ; `--portal-demo` **30/30** / **32/32** ; `--backdrop-demo` **15/15** / **22/22** (la doc disait 21 : **sous-comptage** de la session 30 — 22 appels à `check()`, inchangés) ; `--crash-demo` **20/20** (elle tourne à nouveau) ; compteurs **identiques** pour `--persist-demo` 26, `--nav-demo` 22/29, `--rules-demo` 28, `--snapshot-demo` 11, `--screen-demo` 19, `--product-probe` 16. `%APPDATA%/StarFish/` **sans marqueur**, document utilisateur **non réécrit**. **Prémisses prouvées** : branche F-011 neutralisée → `rc=1`, **exactement 3 `FAIL`** ; connexion de rendu neutralisée → **exactement 1 `FAIL`**.

34. **Session 32 — T-041 : le fond *est* le bureau, donc les gestes du bureau vide n'ont plus besoin d'un hook global** (détail : `devlog/2026-10-16.md` et §21 de `docs/technique.md`). `docs/produit.md` donnait **F-001** (« glisser sur le bureau vide ») et **F-022** (« double-clic sur le bureau vide ») depuis l'origine, et les deux avaient l'air d'exiger un hook souris global (**T-028**) parce que le bureau vide appartient à `SysListView32`, une fenêtre d'un **autre processus**. T-039 a **supprimé le problème au lieu de le résoudre** : le fond est une fenêtre plein écran de nous, donc le geste démarre **dans une de nos fenêtres**. T-028 ne se justifie plus que pour un geste parti hors de nos fenêtres.
    - **La machine à états est pure** (`src/ui/backdrop_gesture.hpp`, header-only) : `press` / `move` / `release` / `doubleClick` avec un point en **pixels d'écran virtuel** (l'espace des cellules du fond *et* des rects stockés — T-014) et un booléen « ce point est sur une des icônes que le fond dessine ». `DesktopBackdrop` ne fait plus que de la plomberie, et les règles se testent **sans bureau**. **20 cas** `ctest`.
    - **Les refus sont la moitié du travail.** Sur un bureau, une création non demandée est le bug coûteux, donc cinq situations sont explicitement vérifiées comme ne créant **rien** : un **clic** (press + release sans mouvement), un **mouvement sous le seuil** (6 px), un **press sur une des icônes du fond** (elles appartiennent au bureau ; leur comportement est T-042, et une zone dessinée par-dessus une icône serait non demandée), un **rectangle plus petit que la taille minimale** (160×120 — le **grossir** au minimum poserait une zone là où l'utilisateur n'en a pas dessiné), et un **double-clic sur une icône** (F-022 dit « bureau **vide** »). Le minimum n'est **pas recopié** : `ProductApp::wireBackdrop()` lit `container->minimumFenceSize()`, donc le geste et le conteneur ne peuvent pas diverger sur ce qu'est une zone.
    - **Le clic-through devient une conséquence, pas un état.** Le fond était click-through parce qu'il n'avait rien à répondre ; la bonne formulation devient **« il prend la souris là où il a une réponse »**. `setGestureEnabled(true)` fait `setClickThrough(false)` **et** `setInputTarget(this)` — les deux moitiés de la même décision — et `false` remet les deux.
    - **⚠️ Correction la moins visible de la session — le `IDropTarget` OLE se découple du click-through.** `attach()` l'enregistrait **si la surface n'était pas click-through** : vrai tant que les seules surfaces non-click-through étaient des zones, et que toute zone a un handler de drop. Le fond casse cette équivalence — il **prend** la souris et n'a **aucun** comportement de dépôt — donc avec l'ancienne condition il se serait enregistré comme cible et aurait **avalé un dépôt qu'il ne peut pas honorer**, exactement la régression silencieuse que T-052 documente. La condition devient **« un handler de drop existe »**, ce qui est la vraie raison d'enregistrer une cible de drop. Vérifié en `--host` (`the backdrop still swallows no drop`).
    - **Du geste au document sans conversion.** Le geste est mesuré **à l'écran** (`event->globalPosition()`, règle de T-043) et le fond poste des positions écran **physiques** — exactement l'espace d'un rect stocké (T-014). `ProductApp::onFenceDrawn(rect)` crée donc la zone **là où elle a été dessinée** : aucun placement par défaut, aucune aimantation, et la politique de nommage est partagée avec le tray et les réglages (`nextFenceTitle()`).
    - **L'aperçu est peint, et pas seulement mémorisé** : la bande élastique entre dans la frame (bordure pointillée + remplissage translucide, délibérément pas la couleur d'un panneau : c'est un aperçu de **geste**), mesuré par la sonde — **231 738 → 273 665** pixels opaques (+41 927). Le rendu reste **coalescé à 120 ms** : un drag émet ~60 mouvements par seconde et chaque rendu téléverse l'écran virtuel entier.
    - **Nouveau prix assumé** : le **menu contextuel du bureau vide** (« Nouveau > », « Actualiser », « Paramètres d'affichage ») est perdu pour la même raison que le dépôt — il venait de `DefView`, masquée — et c'est aussi la moitié « **ou menu contextuel** » de F-001 → **T-054**.
    - **Vérification** : build MinGW **0 warning** ; `ctest` **13/13** (`ui_backdrop_gesture` : **20 cas**) ; `--backdrop-demo` **31/31** headless / **40/40** `--host` (15/22 avant : **+16 / +18**) ; compteurs **identiques** pour tout le reste (`--fence-demo` 17/18, `--persist-demo` 26, `--nav-demo` 22/29, `--rules-demo` 28, `--portal-demo` 30/32, `--snapshot-demo` 11, `--screen-demo` 19, `--product-probe` 16) ; `%APPDATA%/StarFish/` **sans marqueur**, document utilisateur **non réécrit**. **Prémisses prouvées** : `iconAt()` → `-1` ⇒ `rc=1`, **1 `FAIL`** — et c'est **la prémisse elle-même** : la sonde **refuse de mesurer** au lieu de passer à vide (2 `FAIL` unitaires sur 20) ; refus de taille neutralisé ⇒ **2 `FAIL`** (dont une cascade) et 1 `FAIL` unitaire ; émission de `fenceDrawRequested` neutralisée ⇒ **7 `FAIL`** (toute la chaîne F-001 + trois cascades).
    - **⚠️ `--crash-demo` est retombée dans le panneau d'environnement de la session 30** : `rc=1`, **3 `FAIL`** en cascade derrière `the victim starts` (`QProcess` ne peut pas créer son tube stdio). **Vérifié sur la révision non modifiée** (`git stash -u` + rebuild, même commande) : **échec identique** → pas une régression de T-041. C'est la même instabilité qu'en session 30, apparue et disparue toute seule.
    - **Reste humain** : le geste **au vrai curseur** — dessiner une zone sur le bureau (avec *Hide desktop icons* actif) et double-cliquer pour masquer/afficher. La sonde prouve le câblage, le modèle et les refus ; elle ne dit pas si **6 px** est le bon seuil au doigt.

## À ne pas faire

- Ne pas pousser sur un remote GitHub sans accord explicite.
- Ne pas valider un placement par le seul z-order ni par une fenêtre de test de la même couleur que le fond (faux positif de la session 4), **ni par une capture d'écran sans vérifier que le bureau est visible** (faux négatif de la session 7 : navigateur maximisé ; session 8 : `Win+D` **restaure** les fenêtres déjà minimisées — ne pas le presser si le bureau est déjà visible).
- Ne pas retirer `starfish.rc` / `starfish.manifest` du build : la panne (zones invisibles) est totalement silencieuse. Idem, un manifeste XML **ne peut pas contenir `--` dans un commentaire** (Windows refuse alors de démarrer le binaire, avec un message qui n'a rien à voir).
- Ne pas tenter d'**ajouter** `WS_EX_LAYERED` après le reparentage sur un binaire sans manifeste, ni d'appeler `UpdateLayeredWindow` sur une fenêtre hébergée créée par Qt : refus silencieux / `ERROR_INVALID_PARAMETER`.
- Ne pas tenter de valider T-021/T-017/T-018/T-019 **ni le geste souris de T-007 sur le bureau hébergé** depuis l'agent : le bureau est recouvert et le `Win+D` de la sonde est sans effet depuis un processus non-foreground. C'est une validation humaine (bureau libre + yeux). La sonde `--fence-demo` prouve le **câblage**, pas le ressenti.
- Ne pas faire confiance à `export PATH` du bash agent pour lancer `starfish.exe` (DLL MinGW non trouvées) : utiliser `dangerouslyDisableSandbox` ou PowerShell avec `$env:PATH`. Ne pas attendre que le tool PowerShell affiche le stdout d'un exe GUI (subsystème WIN32) — les *fichiers* écrits par l'exe, si. Et le sandbox bloque le lancement même avec le bon `PATH` : `Start-Process -Wait` + `dangerouslyDisableSandbox: true`.
- Ne pas lancer les sondes depuis `build/` : elles écrivent leur rapport en **chemin relatif** (`build/xxx_demo.txt`), donc le rapport atterrit dans `build/build/` et l'ancien reste périmé — avec un `exit 0` trompeur. Toujours les lancer depuis la racine du dépôt. Et ne pas conclure « la sonde ne produit rien » : un `QFile` qui ne peut pas créer son dossier échoue **en silence**.
- Ne pas croire que `build/starfish.exe` a besoin du `PATH` Qt : l'étape `POST_BUILD` (`windeployqt`) déploie le runtime à côté du binaire (décision 18). Si le message « Qt6Widgets.dll introuvable » réapparaît, c'est que le build n'a pas été relinké depuis un `clean` — relancer `cmake --build`.
- Ne pas faire déplacer un fichier sur le disque par une règle : `applyRulesTo()` range un item dans une zone, point. `moveFiles` est persisté mais **sans effet** (T-031) — et une sonde doit continuer de **prouver** que le fichier est resté à son chemin d'origine.
- Ne pas faire dépendre un critère de règle du **nom d'affichage** du Shell : le Shell masque l'extension des types connus, donc un critère de type ne correspondrait jamais. `fileMetaFromItem()` passe le nom de fichier du disque, extension comprise.
- Ne pas persister le **contenu** d'un portail comme items `"file"` : le listing est relu du disque, seul le chemin du dossier va dans le document (`{"kind":"portal","path":…}`). Le figer produirait des doublons au rechargement et un miroir gelé (ADR-7, §13). Et ne pas **nettoyer** le chemin déclaré (`QDir::cleanPath` transforme `C:\x` en `C:/x`) : le document cesserait de faire l'aller-retour octet pour octet. Comparer deux dossiers avec `core::sameFolder()`, jamais par égalité de chaînes.
- Ne pas laisser un portail disparaître du document parce que son dossier est injoignable : `Portal::error` se signale, la liste reste vide, l'entrée reste. Ne pas non plus vider ni supprimer un dossier cible depuis une sonde — `--portal-demo` ne supprime que les fichiers qu'il a créés (nommés d'après son PID).
- Ne pas faire **écrire** un portail : déposer un fichier sur une zone-portail l'ajoute comme tuile, il ne le range pas dans le dossier (T-036, même famille que T-031). Aucune sonde ne doit déplacer un fichier.
- **Ne pas oublier qu'une zone hébergée affiche une *image*.** Le `paintEvent` du widget ne va **jamais** au bureau : tout changement de contenu doit repasser par le rendu hors écran. La connexion `contentChanged → renderFence` posée dans `addFence()` est ce qui le garantit (T-040) — ne pas la retirer, et ne pas rajouter un `renderFence()` local « au cas où » : un seul chemin doit mener le contenu à l'écran (c'est la duplication de chemins qui avait laissé le bug de T-045 vivre).
- **Ne pas écrire une vérification de sonde qui dépende de la taille de l'écran** : ni un rect en dur, ni un seuil « en pourcentage de l'écran ». Elle deviendra rouge sur un autre bureau **pour une raison qui n'a rien à voir avec le code** (arrivé en session 31 : deux `FAIL` sur 1920×1080 alors que le code n'avait pas bougé — le dénominateur avait changé, pas la frame). Dériver du `desktopBounds()` mesuré, et d'un budget calculé depuis la géométrie réelle (cellules, zone, nombre d'entrées).
- **Ne pas laisser sortir une tuile qu'un portail fournit** : `releaseItems()` la refuse parce qu'elle appartient au **dossier**, et le prochain rafraîchissement la remettrait aussitôt (T-011). Une icône qui « revient toute seule » se lit comme un bug, pas comme une règle.
- Ne pas émettre un signal **au milieu d'une mutation** : `appendItems()` émet `contentChanged()`, que le produit écoute pour lire `toLayout()` et sauvegarder. L'état doit être cohérent **avant** le signal (le portail est enregistré avant ses tuiles). Le piège symétrique est celui de l'ordre d'évaluation des arguments d'un `check()` (décision 17) : dans les deux cas, quelque chose est lu trop tôt.
- Ne pas conclure d'un chemin avec `QFileInfo(path).absolutePath()` : c'est le **parent**. Pour tester qu'une tuile est *dans* un dossier, comparer `QFileInfo(item.path).absolutePath()` (parent de la tuile) avec `QDir(folder).absolutePath()` (le dossier).
- Ne pas oublier que le `DesktopWatcher` a **deux** signaux qui ne disent pas la même chose : `itemsAdded()` = « ces entrées sont nouvelles » (règles), `folderChanged()` = « ce dossier a changé, peu importe comment » (portails, qui re-listent et ont donc besoin des **suppressions**). Et ne pas oublier d'élaguer la ligne de base sur suppression, sinon un fichier recréé sous le même nom ne serait plus jamais signalé.
- Ne pas donner à `DesktopWatcher` une ligne de base vide : sans instantané pris au démarrage, tout le bureau serait signalé comme « nouveau » à chaque lancement et les règles re-rangeraient tout. Et ne pas calculer le diff à la réception de l'événement plutôt qu'au debounce : un fichier créé puis supprimé serait signalé à tort.
- Ne pas faire écrire `--rules-demo` n'importe où : il ne crée que des fichiers nommés d'après son PID, ne supprime que ceux-là, et n'efface jamais un dossier passé en `--watch`. Idem pour toute sonde future : le bureau de l'utilisateur n'est pas un brouillon.
- Ne pas recréer de doc sans mettre à jour `STATE.md` en parallèle.
- Ne pas modifier l'inventaire fonctionnel sans créer/mettre à jour la `F-xxx` correspondante dans `TODO.md`.
- Ne pas écrire le layout à chaque changement (un drag en émet ~60/s) et ne pas écrire un document identique : passer par `LayoutStore::setLayout` + `scheduleSave`. Ne jamais remplacer le layout courant par du vide quand le fichier est illisible — c'est une perte de données silencieuse. Ne pas faire dépendre la composition d'une zone du contenu du disque : le document est l'autorité (ADR-7).
- Ne pas réécrire le `rect` d'une zone pour l'enrouler : le roll-up ne change que le rect **visible** (`FenceGeometry::visibleRect`), le rect stocké reste le corps déplié (ADR-8). Ne pas non plus faire déplacer/s'enrouler une `FenceView` elle-même : elle signale, le conteneur décide.
- Ne pas oublier que le watchdog 2 s de `DesktopSurface` **ré-applique le placement** : tout état de navigation (masqué, surélevé) doit être honoré par `place()` **et** par la garde `WM_WINDOWPOSCHANGING`, sinon la zone masquée réapparaît ou le Peek est annulé au bout de 2 s.
- Ne pas compter sur `Win+Space` pour Peek : Windows le réserve au sélecteur de langue et `RegisterHotKey` le refuse (mesuré). Et ne jamais avaler un échec d'enregistrement de hotkey — le laisser remonter.
- Ne pas écrire `check(étape, mutation() && lecture(), détail(lecture()))` dans une sonde : l'ordre d'évaluation des arguments est **non spécifié**, le détail peut afficher une valeur d'avant la mutation alors que le test passe (faux rapport). Une mutation = une instruction. Ne pas confondre `QRect::bottom()` (inclusif, `y + h - 1`) et l'alignement de `snap()` (sur `y + h`).
- Ne pas remettre `bg`/`#1F2937CC` (ordre RGBA) dans le schéma : `style.background` est en **`#AARRGGBB`**, la seule forme que `QColor::name(QColor::HexArgb)` relit sans perte.
- Ne pas décider du contenu d'un fichier JSON en lisant un **préfixe d'octets** : `QJsonObject` **trie ses clés**, donc `snapshot` est écrit **en dernier** et une fenêtre de 4096 octets le manque dès que la disposition dépasse ~4 Ko (l'export écrasait une snapshot, l'import l'avalait, et le test passait parce que sa fixture était petite). Pour distinguer une snapshot d'une disposition : **parser** (`hasSnapshotEnvelope`). Et un test de ce genre doit **prouver sa prémisse** (le marqueur est bien au-delà de la fenêtre), sinon il redevient vert pour la mauvaise raison.
- Ne pas écrire `QLatin1String("...").arg(<entier>)` : `QLatin1String` n'a pas de surcharge entière, la conversion vers `QChar` est **ambiguë** et la compilation échoue (rencontré sur `src/main.cpp`). Utiliser `QString::number(...)`.
- Ne pas importer un **fichier de snapshot** comme disposition, ni écraser un fichier de snapshot par un export : l'enveloppe (date, note) serait perdue en silence. `importLayout` et `exportLayout` le refusent explicitement — ne pas retirer ces gardes.
- Ne pas laisser une sonde écrire dans le vrai `%APPDATA%` sans nettoyer : `--snapshot-demo` supprime la snapshot **et** le fichier exporté qu'il a créés, comme `--rules-demo` / `--portal-demo` ne touchent que leurs propres fichiers.
- Ne pas oublier la **capture souris** sur une fenêtre hébergée : sans `SetCapture`, Windows cesse d'envoyer `WM_MOUSEMOVE` dès que le curseur sort du rectangle, et un déplacement de zone meurt au premier pixel franchi (mesuré : une zone hébergée était **impossible à bouger**, et aucune sonde ne pouvait le voir puisqu'elles envoient leurs `QMouseEvent` directement au widget). Le relâchement doit être rendu (`ReleaseCapture` au button-up) et un `WM_CAPTURECHANGED` doit **terminer** le geste (`releaseStuckGesture()`), sinon une zone à demi tirée continue de suivre le curseur sans bouton enfoncé.
- Ne pas restaurer les icônes natives sans savoir si **on** les a masquées : un `ShowWindow(SW_SHOW)` inconditionnel au shutdown réafficherait les icônes d'un utilisateur qui les avait cachées lui-même. `ProductApp` ne restaure que ce qu'il a masqué (`m_iconsHidden`) et, si l'appel échoue, laisse la case décochée plutôt que de mentir.
- Ne pas refaire de `starfish.exe` un binaire qui « démarre et quitte » : **sans argument, c'est l'application**. Les points d'entrée non interactifs sont `ctest`, les sondes `--xxx-demo` et `--product-probe`.
- Ne pas faire décider le tray ni les réglages : `TrayIcon` et `SettingsDialog` **signalent**, `ProductApp` applique — même règle que « le widget signale, le conteneur décide » (décision 15).
- Ne pas déduire le type d'une variable de la **façon dont elle est appelée** : `host` dans `main.cpp` était un `bool` (nommé comme un pointeur) — un « correctif » fondé sur cette lecture a cassé la compilation. **Lire la déclaration** avant d'affirmer un type ; et si le nom induit en erreur, c'est le **nom** qu'il faut changer (fait : `hosted`).
- Ne pas mélanger les deux espaces de coordonnées (T-014a) : **rects, document, `SetWindowPos`, `UpdateLayeredWindow` et messages souris sont en pixels PHYSIQUES** (espace client de `Progman`) ; Qt raisonne en **logique**. Un `QScreen::geometry()` pris tel quel comme rect de zone, ou une coordonnée souris non divisée par le DPR, donnent un décalage **invisible à 100 %** et faux à 150 %. Les deux conversions vivent dans `ProductApp::screenLayout()`, `FenceContainer::renderFence()` et `DesktopSurface::forwardMouse` — nulle part ailleurs.
- Ne pas clamer une zone dans le **rectangle englobant** de tous les écrans : dès que deux écrans ont des tailles différentes, ce rectangle contient des **zones mortes** qu'aucun moniteur ne dessine. Le clamp se fait dans l'écran du **centre** (`ScreenLayout::clampRectFor`).
- Ne pas déduire `FenceWindow::monitor` d'autre chose que du **rect** : c'est l'indice de restauration de `restoreRect()`, et un nom qui ment fait revenir la zone sur le mauvais écran au démarrage suivant.
- Ne pas déclarer la mise à l'échelle de la peinture **sans la mesurer** : c'est désormais **mesuré** (`--screen-demo` : bordure de 1,0 px logique → 1,00 / 1,50 / 2,00 px physiques à `dpr` 1 / 1,5 / 2, prémisse prouvée en cassant la conversion). Si `renderFence` cesse de poser `setDevicePixelRatio(dpr)`, la sonde doit repasser au **rouge** — ne pas « réparer » la sonde à la place du code, et ne pas retirer cette mesure en la croyant acquise.
- Ne pas présenter le **contexte d'awareness DPI** comme acquis : il est **lu** par la sonde (`PER_MONITOR_AWARE (2)` sur la machine de dev — **pas** `PER_MONITOR_AWARE_V2`, contrairement à ce qu'on prêterait à Qt 6). Ne pas ajouter d'entrée `dpiAware` au manifeste sans re-mesurer : le DPI avait été **écarté par la mesure** comme cause des refus de `WS_EX_LAYERED` (ADR-4 finding 4), et Qt 6 ne s'en trouve pas empêché.
- **Ne pas croire qu'une zone hébergée reçoit la souris parce qu'elle est dessinée** : mesuré (session 25), sous la couche d'icônes visible la fenêtre **visible** la plus haute au centre d'une zone est `SHELLDLL_DefView`, puis `SysListView32` — le clic va à la liste du bureau. **Masquer les icônes natives (ADR-3) n'est pas cosmétique : c'est la condition pour qu'une zone serve à quelque chose.** Corollaire : ne pas régler ce problème en posant les zones **au-dessus** de la couche native (option B d'ADR-9) — le même fichier serait dessiné **deux fois** (icône native + tuile).
- **Ne pas mesurer l'atteignabilité d'une fenêtre sans filtrer `IsWindowVisible`** : une fenêtre **masquée** reste dans `EnumChildWindows` et dans `WindowFromPoint`-like, donc la mesure ne distingue plus « je viens de masquer la couche » de « rien n'a changé » (rencontré en session 25 : la pile de z-order était identique avant et après le masquage, ce qui a failli faire conclure à tort).
- **Ne pas prendre `WindowFromPoint` pour une validation au curseur** : il renvoie la fenêtre qui **serait** cliquée, et une fenêtre d'application au premier plan masque la réponse (mesuré : `Chrome_WidgetWin_1`). C'est un proxy — la validation au vrai curseur reste humaine (T-021).
- **Ne pas mesurer un geste dans le repère de l'objet qu'il déplace.** `FenceView` calculait le delta depuis `event->pos()` (widget), alors que le widget **se déplace sous le curseur** : le déplacement appliqué vaut `réel − appliqué` et **converge vers la moitié** de la distance parcourue, en saccades (T-043, ressenti par l'utilisateur). Le repère d'un geste est l'**écran** (`event->globalPosition()`) — et toute sonde qui teste un geste doit envoyer une **séquence** de mouvements dont les coordonnées locales sont recalculées à chaque étape, pas un seul.
- **Ne pas peindre une géométrie locale dans le repère du widget.** `IconGrid::paint()` dessinait les cellules d'`IconLayout::compute()` (espace **local au contenu**, celui de `hitTest`) sans `painter.translate(contentRect.topLeft())` : toute la grille tombait 42 px trop haut et le clip **tranchait** la première rangée (T-045, vu par l'utilisateur). Quand deux consommateurs partagent un calcul, **le second qui ne translate pas est le bug** — `paintDropIndicator` le faisait déjà.
- **Ne pas borner une vérification par le clip.** La première vérification de T-045 comptait les pixels de la bande de la barre de titre, **au-dessus du clip** — donc vide quoi que fasse le painter : elle **passait avec le bug**. Une vérification doit porter sur la plage où les pixels **faux atterrissent** (ici : le premier pixel peint doit être **strictement sous** le haut du contenu ; avec le bug il vaut **exactement** ce haut). Corollaire : une vérification qui ne peut pas échouer ne mesure rien (même leçon que la décision 25). Et pour rester robuste, comparer **deux rendus de la même zone** (avec et sans tuiles) plutôt que supposer une couleur d'icône.
- **Ne pas lancer deux instances de l'application** : elles se disputent le **document** (dernier écrivain gagne) et l'**état des icônes natives** (chacune restaure ce que l'autre croyait masqué). Le garde mono-instance (T-044) est dans le **mode produit seulement**, pour que les **sondes** restent utilisables pendant qu'une application tourne — ne pas le déplacer avant les sondes, ni y ajouter de boîte de dialogue (elle rendrait le garde non testable sans intervention humaine).
- Ne pas retirer `if(MSVC) target_link_options(starfish PRIVATE "/MANIFEST:NO")` de `src/CMakeLists.txt`, ni le pas de CI qui relit le manifeste du binaire : sans le premier, MSVC **génère un second manifeste** et le link échoue (`CVT1100`/`LNK1123`) ; sans le second, le manifeste pourrait disparaître **en silence** et les zones ne s'afficheraient plus (ADR-4).
- Ne pas pousser la documentation seule en la croyant sans effet : **tout push déclenche la CI** (build MSVC ~5 min). Pour un commit de doc, le seul enjeu est de ne pas laisser la CI rouge.
- Ne pas réécrire l'historique du remote : `origin/main` contient un commit de départ (`Initial commit`, README auto-généré). Le dépôt local et le remote ont été joints par un **merge**, pas par un rebase/force-push. Ne pas pousser de jeton ni de secret : l'authentification se fait par `gh` (keyring), jamais par une URL contenant un jeton.
- Ne pas matérialiser une zone de premier lancement **remplie** du bureau : y verser les fichiers revendiquerait des icônes que l'utilisateur n'a pas mises là. *(La raison historique — « aucune représentation d'une icône hors zone » — n'est plus vraie depuis T-039, mais la règle tient : une zone neuve n'a pas à revendiquer quoi que ce soit.)*
- **Ne pas masquer les icônes natives sans que le marqueur soit écrit** (T-046), et **ne pas retirer le marqueur avant que la couche soit rendue** : l'ordre write-ahead / write-behind est ce qui garde tout plantage intermédiaire **réparable**. Un `setDesktopIconsHidden(true)` qui ne peut pas écrire le marqueur **refuse** de masquer (il retourne `false`) — ne pas « réparer » ça en masquant quand même : c'est le seul chemin vers l'état irréparable (bureau sans icônes **et** sans note).
- **Ne pas faire dépendre la réparation du démarrage d'un état en mémoire** (booléen, statique, « je me souviens ») : elle lit le **fichier**, point — c'est ce qui la rend valable après un `kill` (`--crash-demo` le mesure). Et **ne pas supprimer le marqueur quand la restauration échoue** : le prochain lancement (ou « Restore my icons ») doit encore pouvoir réparer.
- **Ne pas ranger le marqueur dans le dossier de `--layout`** : la couche d'icônes appartient à la **session**, pas à un document — le marqueur vit à `%APPDATA%/StarFish/icons-hidden.marker` quel que soit le document utilisé.
- **Ne pas mesurer `--crash-demo` avec les icônes déjà masquées** : la sonde exige de les voir **visibles** au départ et s'arrête en le disant (c'est sa prémisse). Ne pas retirer non plus ses vérifications « la fin était vraiment brutale » (marqueur encore là, icônes encore masquées) : sans elles, la sonde passerait au vert sur un processus qui a eu le temps de se démonter proprement. Et elle ne rend que ce qui est **à elle** (couche masquée **avec** marqueur) : ne pas l'élargir à « montre les icônes » — l'état de l'utilisateur n'est pas son brouillon.
- **Ne pas remettre une réparation « conditionnelle » dans `ProductApp::start()`** (du genre « seulement si `hostOnDesktop` », ou « seulement si le document a des zones ») : la couche d'icônes absente est un fait de la **machine**, pas de ce document ni de ces options — la sonde `--crash-demo` mesure la réparation en mode headless **exprès**.
- **Ne pas faire dessiner au fond autre chose que les icônes qu'aucune zone ne détient** : l'ensemble est **calculé** (`BackdropLayout::freeItems`) à chaque changement et **stocké nulle part**. Le persister ferait entrer les icônes du bureau dans le document (ADR-7 cassé), figerait la liste au moment de l'écriture, et F-007/F-011 cesseraient de tomber tout seuls. Ne pas non plus dessiner **toutes** les entrées en comptant sur les zones pour les recouvrir : une icône réclamée par une zone resterait dessinée **sous** elle et réapparaîtrait au premier déplacement.
- **Ne pas comparer deux chemins d'icône par égalité de chaînes** : le Shell et le scan peuvent renvoyer deux orthographes du même fichier (casse, séparateur), et la comparaison stricte le dessinerait **deux fois** — une fois dans la zone, une fois sur le fond. Utiliser `BackdropLayout::pathKey()` (comparaison **seulement** : la clé n'est jamais écrite, sinon l'aller-retour octet pour octet du document serait cassé).
- **Ne pas réutiliser `IconLayout` pour le fond** : la grille d'une zone remplit des **lignes**, le bureau Windows remplit des **colonnes**. Deux règles, deux implémentations — et le test `cellsFillColumnsNotRows` doit rester rouge si on revient à l'autre (prémisse vérifiée : `rc=2`, deux `FAIL`).
- **Ne pas héberger le fond en mode opaque.** Il couvre **tout l'écran virtuel** : sans `UpdateLayeredWindow`, il cacherait le papier peint. `DesktopBackdrop::attach()` relit donc `perPixelAlpha()` après l'hébergement et **refuse** si le push n'a pas pris — et `ProductApp` **ne masque alors pas** la couche native. Même discipline que le marqueur de T-046 : **si le geste sûr est impossible, on refuse le geste risqué**. Ne pas non plus inverser l'ordre du retour (la couche native revient **d'abord**, le fond part ensuite) : l'inverse laisserait le bureau sans icônes le temps d'un aller-retour.
- **Ne pas rendre le fond cliquable avant qu'il ne sache faire quelque chose** — et depuis **T-041** il sait : les gestes du **bureau vide** (drag = créer une zone, double-clic = quick hide) sont exactement ce qui justifie de prendre la souris. Ce qui reste interdit, c'est de prendre un geste **qu'on ne saurait pas honorer** : un clic sur une des icônes du fond ne fait toujours rien (**T-042**), et **le fond ne doit enregistrer aucune cible de drop** — c'est pour cela que `attach()` enregistre le `IDropTarget` OLE **si un handler de drop existe** et non « si la surface n'est pas click-through » (T-052 : avaler un dépôt qu'on ne peut pas honorer serait une régression silencieuse).
- **Ne pas ré-attacher le fond à chaque `refresh()`** : un drag de zone émet ~60 changements par seconde et un rendu téléverse l'écran virtuel entier (14 Mo à 2560×1440). Le rendu est **coalescé** (`kRenderCoalesceMs = 120`) et `setOccupiedPaths()` **sort tôt** si l'ensemble n'a pas changé — ne pas retirer l'un ou l'autre.
- **Ne pas lancer une sonde dans une boucle sans vérifier qu'on lui passe bien un argument** : un `Start-Process` dont l'argument s'est perdu démarre `starfish.exe` **sans argument**, c'est-à-dire **l'application réelle** sur le bureau de l'utilisateur (constaté en session 30 : vrai document chargé, zones hébergées, tray et hotkeys). Les sondes se lancent avec une liste d'arguments **explicite**, et on relit le code de sortie **et** le fichier de rapport.
